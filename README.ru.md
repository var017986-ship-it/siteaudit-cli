# SiteAudit

CLI-чекер безопасности веб-сайтов на Python. Один CLI объединяет ограниченный обход одного хоста, проверки HTTPS/заголовков/cookie, проверки служебных путей в духе Nikto, признаки проблем параметров в духе Wapiti, пассивные проверки ответов по мотивам ZAP, модульные проверки в духе W3AF и локальные буквальные шаблоны по мотивам Nuclei (JSON и ограниченное подмножество YAML).

Это учебный проект и основа для дальнейшего развития, а не замена профессиональному пентесту или полноценным сканерам OWASP ZAP, Nuclei, Nikto и Wapiti. Чекер не обещает найти все уязвимости. Для каждой находки указывает URL, наблюдаемые признаки, серьёзность, уверенность и совет по исправлению.

## Используйте только с разрешения

Проверяйте только сайты, которыми владеете, или сайты, на проверку которых у вас есть явное разрешение. Чекер ограничивает запросы указанным хостом и глубиной обхода. Он не подбирает пароли, не загружает файлы и не пытается выполнять команды. POST-проверки выключены по умолчанию; флаг `--post-probes` отправит не более одного запроса с маркером в каждую из пяти найденных форм и может создать данные в приложении. GET-маршруты тоже иногда меняют данные, поэтому запускайте чекер только на целях, где допустимы такие особенности. Отражение строки и сообщение базы данных — признаки для ручной проверки, а не доказательство эксплуатации.

## Требования

- Python 3.11 или новее
- Сторонние Python-пакеты не нужны

## Установка

```powershell
python -m pip install -e .
```

В Windows запустите `setup.bat`, затем `start.bat`: setup предлагает вариант 1 для базовой установки и вариант 2 для подготовки внешних движков. Меню сканирования предлагает быстрый пассивный, обычный, глубокий, полный комбинированный режим, режим только внешних движков и отдельную проверку готовности сканеров. Полный режим запускает встроенные проверки и доступные внешние сканеры; режим upstream-only пропускает встроенный обход. Оба режима включают активный ZAP, если он установлен. Недостающие движки появятся в JSON со статусом `unavailable`. Консоль показывает прогресс и приблизительное оставшееся время; внешняя оценка основана на лимитах времени, поэтому скан часто завершается раньше.

Перед полной проверкой запустите `siteaudit --doctor`: команда без сетевого сканирования проверит доступность движков, шаблонов Nuclei, WSL-версии ZAP и Docker-образов. `start.bat` выполняет эту проверку заранее и спрашивает, продолжать ли доступными движками, если часть не установлена.

Чтобы установить доступные движки в Windows, запустите `setup-engines.bat`. Скрипт проверяет SHA-256 официального Nuclei v3.11.1, устанавливает бинарник и набор шаблонов в `%LOCALAPPDATA%\SiteAudit\engines`, ставит Wapiti 3.3.2 в отдельное окружение Python 3.12–3.14, а также устанавливает закреплённые Nikto 2.6.1 и OWASP ZAP 2.17.0 в Debian WSL, если этот дистрибутив доступен. При запущенном Docker Desktop скрипт также загружает официальные образы Nikto и ZAP как запасной способ запуска. Исходники и архивы движков остаются вне репозитория. Docker Desktop и W3AF скрипт не устанавливает; для W3AF нужен отдельный Linux/macOS runner. Установка не сканирует сайты.

## Запуск

```powershell
siteaudit https://example.com --output report.json
```

Чтобы дополнительно отправить безвредный маркер не более чем в пять найденных POST-форм (это может создать данные на сайте):

```powershell
siteaudit https://example.com --post-probes --output report.json
```

Для повторной boolean-проверки SQL-инъекций максимум в двух числовых GET-параметрах (значение запроса изменяется и может повлиять на поведение приложения):

```powershell
siteaudit https://example.com --sqli-probes --output report.json
```

Чекер сравнивает исходный ответ с двумя истинными и двумя ложными числовыми условиями. Он не использует задержки, извлечение данных, внешние callback-запросы или команды записи.

Отдельный флаг `--graphql-probe` проверяет, возвращает ли GraphQL endpoint имя типа запросов при introspection. Он отправляет до трёх фиксированных read-only POST-запросов на том же хосте, без cookies и авторизации; результат считается информационным:

```powershell
siteaudit https://example.com --graphql-probe --output report.json
```

Добавить локальные JSON-шаблоны или шаблоны Nuclei YAML из поддерживаемого подмножества можно через `--templates-file`; формат и ограничения описаны в [docs/custom-templates.md](docs/custom-templates.md). Для YAML установите необязательную зависимость: `python -m pip install -e ".[yaml]"`.

Или без установки команды:

```powershell
python -m siteaudit https://example.com --output report.json
```

Флаг `--help` показывает настройки скорости, глубины и ограничений обхода. По умолчанию запускаются ограниченные шаблонные проверки, проверки путей и GET-параметров. Флаг `--passive` отключает эти адресные пробы и оставляет обход и анализ полученных ответов. Для локальных и частных IP нужен явный `--allow-private`.

Значения параметров URL в сохранённом отчёте скрываются. В отчёте всё ещё могут быть домен и технические сведения о сервере, поэтому обращайтесь с ним аккуратно.

## Подключение upstream-сканеров

В отчёте верхний `status` будет `partial`, если исчерпан встроенный лимит запросов или внешний движок завершился с ошибкой, таймаутом, блокировкой границ либо недоступностью. JSON сохраняется, а CLI возвращает код 1. Встроенные `--max-pages`, `--max-depth` и бюджет запросов относятся к проверкам SiteAudit. Внешние сканеры получают собственные настройки: ZAP ограничивает глубину и число ссылок на каждой странице, Wapiti — глубину, ссылки на страницу, файлы в каталоге и время; общего жёсткого лимита страниц у них нет. Их фактические ограничения и счётчики прокси записываются отдельно в JSON. Внешний отчёт может показывать ноль встроенных страниц/запросов, даже если сканер выполнил работу: смотрите `summary.plugin_results.external_engines`.

SiteAudit запускает Nuclei, Nikto, Wapiti, OWASP ZAP и W3AF и объединяет их находки со своим JSON-отчётом. Для Windows движки можно подготовить через `setup-engines.bat`; исходники и базы проверок в репозиторий не копируются. ZAP и Nikto работают через Debian WSL, а при наличии Docker Desktop доступны официальные образы. Для всех подключённых движков можно использовать `--engine all`; на Windows W3AF вернёт статус `unavailable`:

```powershell
siteaudit https://example.com --engine all --engine-timeout 300 --output report.json
```

Флаг `--external-only` запускает выбранные upstream-движки без повторного обхода и встроенных проб SiteAudit. В отчёте встроенные страницы/запросы будут равны нулю; счётчики прокси каждого внешнего движка сохраняются отдельно:

```powershell
siteaudit https://example.com --external-only --engine nuclei --engine-timeout 300 --output nuclei-report.json
```

Для Nuclei можно указать локальную папку или файл шаблонов через `--nuclei-templates`; по умолчанию адаптер сначала проверяет набор, установленный `setup-engines.bat`, затем `~/nuclei-templates`. До запуска HTTP-шаблоны копируются во временную папку, а файлы с прямыми сетевыми DSL-функциями `resolve()`, `public_ip()` и `jarm()` исключаются; число исключённых правил попадёт в отчёт. Это защищает от функций Nuclei v3.11.1, способных делать DNS/TLS/HTTPS-запросы вне настроенного прокси. Редиректы и Interactsh выключены. Проверяйте шаблоны до запуска: прокси не видит зашифрованный HTTP-заголовок Host внутри HTTPS CONNECT-туннеля. В Windows `setup-engines.bat` устанавливает закреплённый ZAP 2.17.0 в Debian WSL и проверяет SHA-256 архива; Docker-образ `ghcr.io/zaproxy/zaproxy:stable` остаётся запасным вариантом. По умолчанию ZAP запускается в baseline-режиме: обход и пассивный анализ без активного сканирования. `--engine zap --zap-active` включает активный скан ZAP; он может отправлять атакующие тестовые строки. ZAP baseline требует `--engine-timeout` не менее 120 секунд, активный режим — не менее 180 секунд. Для остальных движков `--engine-timeout` ограничивает время сканирования; Nikto WSL может использовать до 25 дополнительных секунд для завершения и записи отчёта. `--delay` применяется там, где движок его поддерживает. Внешние инструменты используют отдельный лимит транзакций прокси и не делят внутренний бюджет запросов SiteAudit; для HTTPS лимит считает CONNECT-туннели, а не запросы внутри них. Wapiti не поддерживает общий лимит запросов в секунду и жёсткий предел общего числа страниц. В этом проекте Wapiti 3.3.2 проверен на Windows с Python 3.13; upstream FAQ по-прежнему рекомендует WSL, и поведение других версий может отличаться. W3AF работает в старой Linux/macOS-среде и вернёт `unavailable` в Windows; Nikto можно запускать из Debian WSL, нативного Perl-окружения или официального Docker-образа. Nikto записывает совпадения как информационные, потому что его экспорт не содержит нормализованного уровня серьёзности. В JSON-отчёте для каждого запрошенного движка будет статус `completed`, `partial`, `unavailable` или `error`.

Для каждого внешнего движка запускается временный scope-прокси. WSL-движки подключаются через адрес шлюза WSL и разрешённый IP WSL-процесса, а Docker-клиенты ограничены проверенной подсетью bridge-сети и должны предъявить случайный прокси-пароль, созданный на время одного скана. Прокси закрывает активные соединения при завершении скана. Он фильтрует открытые HTTP-запросы и HTTPS CONNECT по заданному хосту и порту, подключается к закреплённому SiteAudit IP и проверяет TLS SNI. Поэтому редиректы на другой хост или порт блокируются, если сканер отправляет их через прокси. В JSON сохраняются счётчики разрешённых HTTP-запросов, HTTPS-туннелей, блокировок и достижения лимита; при блокировке или исчерпании лимита скан помечается как частичный. Содержимое HTTPS остаётся зашифрованным: прокси считает и замедляет туннели, а не отдельные запросы внутри них, и не видит HTTP-заголовки, методы или тела запросов внутри TLS. Сканер или шаблон может передать другой зашифрованный Host или метод на закреплённый IP; прокси не ограничивает HTTP authority внутри TLS. Прокси также не является сетевым firewall и не блокирует все возможные прямые соединения процессов сканеров. Проверяйте шаблоны Nuclei и запускайте движки только на разрешённых целях. Wapiti и W3AF не умеют жёстко ограничить общее число страниц; обходчик W3AF может отправлять заполненные формы. Модуль W3AF `ssl_certificate` отключён, потому что он открывает прямой сокет в обход прокси.

`setup-engines.bat` ставит Wapiti 3.3.2 в отдельное окружение Python; эту версию мы проверили на Windows с Python 3.13. Управляемые бинарники Nuclei и Wapiti ищутся раньше `PATH`; остальные программы можно установить отдельно и добавить в `PATH`. Nikto 2.6.1 устанавливается в Debian WSL и запускается через scope-прокси с ограниченным набором плагинов и Linux-side таймаутом. W3AF требует legacy-среду Linux/macOS и недоступен в нативном Windows. Запуск внешних сканеров активный: используйте их только для сайтов, которые вы вправе проверять.

Фильтр шаблонов Nuclei учитывает [проблему upstream v3.11.1](https://github.com/projectdiscovery/nuclei/issues/7769), из-за которой `resolve()`, `public_ip()` и `jarm()` могли обращаться к сети вне настроенного прокси.

## Что проверяется

- Наличие HTTPS и ошибки TLS; значения CSP и заголовков защиты от встраивания/referrer/permissions — на HTML-документах, `max-age` HSTS — на корне хоста, точное значение `nosniff`; проверки cookie учитывают похожие на сессионные имена, `SameSite=None` без `Secure`, недопустимые SameSite и требования префиксов `__Secure-`/`__Host-`.
- Страницы и GET-формы на том же домене с настраиваемыми пределами глубины и числа страниц.
- Ограниченный кэш ответов в памяти (до 100 ответов и 2 МБ) для пассивных проверок mixed content, слабого CSP, stack trace и CORS-заголовков.
- Небольшой список типовых служебных путей. Проверка использует HEAD без загрузки содержимого и сравнивает ответы со случайным несуществующим путём, чтобы отсеивать типовые soft-404 и SPA catch-all.
- Ограниченные GET-проверки найденных параметров и форм: инертная HTML-метка проверяется как разобранный элемент, одиночная кавычка ищет характерные ошибки базы данных, а параметры перенаправления проверяются на open redirect. По редиректу чекер не переходит; отражённая метка сама по себе не доказывает XSS. `--sqli-probes` включает сравнение повторных истинных/ложных условий максимум для двух числовых GET-параметров.
- Отдельная проверка SSTI посылает только обёрнутые случайными метками арифметические выражения максимум в два нечувствительных GET-параметра и сообщает о проблеме только при совпадении обоих вычисленных результатов.
- Небольшой модульный набор W3AF-подобных проверок: отражение произвольного CORS Origin с credentials и POST-формы без распознаваемого CSRF-поля. Формы только анализируются, запросы POST не отправляются этой проверкой.
- Опциональная проверка GraphQL introspection: один фиксированный read-only запрос максимум к трём endpoint-ам на том же хосте; схема не сохраняется, результат информационный.
- Локальные JSON-шаблоны с методами только GET/HEAD и буквальными проверками статуса, заголовков и ответа. Шаблоны не могут выполнять код или задавать произвольные payload-строки.
- Через `--templates-file` можно добавить до 23 локальных правил. JSON поддерживается всегда; необязательный импортёр принимает ограниченное подмножество Nuclei YAML: фиксированные GET/HEAD пути, положительные body-word и status matcher-ы. Всего не более 32 правил вместе с девятью встроенными.
- JSON-отчёт с серьёзностью, уверенностью, признаками, адресом, советом по устранению и ссылками на источники для шаблонных находок.

Девять встроенных шаблонов проверяют Go pprof и expvar, Spring Boot Actuator mappings, техническую Django 404-страницу при включённом debug-режиме, OpenAPI-спецификации по двум типовым адресам, конфигурацию Git, страницу PHP-информации и Apache server-status. Публичная API-документация отмечается как информационное наблюдение, поскольку часто опубликована намеренно. Ответ анализируется по фиксированным признакам, но его содержимое не копируется в отчёт; это выбранные проверки утечек, а не общая база CVE.

Сверка реализованных возможностей и оставшихся пробелов: [FEATURES.md](FEATURES.md).

Небольшой локальный набор правил и ограниченный импортёр YAML не совместимы с большой базой шаблонов CVE из Nuclei и не заменяют её. Здесь также нет перехватывающего прокси и полного набора правил ZAP; в собственном реестре W3AF-подобных проверок пока два узких плагина, а не сотни. Чекер не может гарантировать, что конкретный GET- или явно включённый POST-маршрут приложения не меняет состояние. Веб-приложения отличаются; важные результаты нужно проверять вручную.

## Разработка

По умолчанию проект использует только стандартную библиотеку Python. Необязательная зависимость PyYAML устанавливается только для импорта ограниченного подмножества Nuclei YAML. Модули используют общий HTTP-клиент и формат находок, чтобы новые собственные проверки можно было добавлять отдельно.
